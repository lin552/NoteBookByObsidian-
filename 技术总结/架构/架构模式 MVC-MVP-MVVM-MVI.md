| **维度**​      | ​**MVC**​                                              | ​**MVP**​                  | ​**MVVM**​                | ​**MVI**​                 |
| ------------ | ------------------------------------------------------ | -------------------------- | ------------------------- | ------------------------- |
| ​**数据流方向**​  | 单向循环（View → Controller → Model → View）                 | 双向（View ↔ Presenter）       | 双向（View ↔ ViewModel，自动绑定） | 单向（Intent → State → View） |
| ​**解耦核心**​   | 分层隔离（View/Controller/Model职责分离，但View与Controller可能直接交互） | 接口抽象（View与Presenter通过接口解耦） | 数据绑定（View与ViewModel无引用）   | 单向流（状态驱动，无直接交互）           |
| ​**状态管理**​   | 分散（Model持有数据状态，View自行管理UI状态，无统一状态源）                    | 分散（View或Presenter持有状态）     | 隐式（ViewModel持有状态，无统一管理）   | 显式（单一State源，全局管理）         |
| ​**生命周期安全**​ | 需手动管理（Controller易持有View引用导致泄漏）                         | 需手动管理（Presenter可能泄漏View）   | 自动（LiveData等感知生命周期）       | 自动（ViewModel生命周期长于View）   |
| ​**可测试性**​   | 中等（Controller可独立测试，但View与Controller耦合可能增加测试成本）         | 高（Presenter无UI依赖）          | 高（ViewModel无UI依赖）         | 高（状态转换可单元测试）              |
| ​**适用场景**​   | 简单应用，逻辑分层清晰，需快速实现（如早期移动端应用）                            | 中小型项目，逻辑简单（需明确职责分离）        | 需高效UI更新，减少模板代码（如现代前端/移动端） | 复杂状态管理（如多交互、共享状态）         |
|              |                                                        |                            |                           |                           |

#### 二、核心定义
##### **1. `MVC`（Model-View-Controller）​**​
##### ​**优点**​
- ​**简单易上手**​：天然适配 Android 原生组件（如 Activity/Fragment 作为 Controller），适合快速开发小型应用。
- **职责初步分离**​：Model 处理数据，View 负责 `UI`，Controller 协调交互，逻辑清晰。
- **低学习成本**​：与 Android 传统开发模式一致，无需额外学习框架。
##### ​**缺点**​
- ​**Activity 肿胀**​：Controller 职责混杂（`UI` 逻辑、业务逻辑、生命周期管理），导致代码冗余。
- **View 与 Controller 耦合**​：Activity 直接操作 View，违反单一职责原则，难以复用。
- **测试困难**​：`UI` 逻辑与业务逻辑混合，单元测试需依赖 Android 上下文，效率低。
​**适用场景**​：简单页面（如登录页）、小型工具类应用。

##### 2）`MVP（Model-View-Presenter）`
##### **优点**​
- ​**解耦彻底**​：View 仅暴露接口，Presenter 处理逻辑，降低耦合度。
- ​**高可测试性**​：Presenter 独立于 Android 框架，可独立单元测试。
- ​**职责明确**​：View 负责渲染，Presenter 负责逻辑，Model 负责数据。
##### ​**缺点**​
- ​**接口爆炸**​：每个 View 需定义大量接口（如 `onDataLoaded()`），增加模板代码。
- ​**Presenter 膨胀**​：复杂页面的 Presenter 可能承担过多逻辑，导致维护困难。
- ​**双向依赖**​：View 和 Presenter 需互相持有引用，需注意内存泄漏。
​**适用场景**​：中大型应用（如电商详情页）、需高可测试性的场景。

##### 3)`MVVM（Model-View-ViewModel）`
##### **优点**​
- ​**数据驱动**​：通过 `LiveData` 或 `StateFlow` 自动同步数据，减少手动更新 `UI` 的代码。
- **解耦彻底**​：View 仅观察 `ViewModel`，`ViewModel` 不依赖 Android 组件，可脱离 `UI` 测试。
- ​**开发效率高**​：结合 Data Binding 或 `Jetpack Compose`，模板代码减少 50% 以上。
##### ​**缺点**​
- **学习成本高**​：需掌握数据绑定、响应式编程（如 `LiveData`、`ViewModel`）。
- ​**调试复杂**​：数据绑定链式调用（如 `Transformations.map`）易引发空指针或内存泄漏。
- ​**过度绑定风险**​：简单页面使用`MVVM`可能引入不必要的复杂度。
​**适用场景**​：复杂 `UI`（如列表、实时仪表盘）、数据驱动型应用。
##### 4）`MVI（Model-View-Intent）`
##### **优点**​
- **状态可预测**​：所有状态变化由 Intent 触发，单向数据流清晰，便于调试。
- ​**严格解耦**​：View 仅渲染状态，Intent 封装用户操作，逻辑集中管理。
- ​**天然支持撤销/重做**​：状态不可变，历史状态可追溯。
##### ​**缺点**​
- ​**实现复杂度高**​：需引入响应式编程（如 `RxJava`、`Flow`），定义大量 State 和 Intent 类。
- ​**样板代码多**​：每个交互需定义 Intent 和 State，简单场景性价比低。
- **学习曲线陡峭**​：需理解函数式编程、不可变数据等概念。


​**适用场景**​：高稳定性需求（如金融交易）、复杂交互（如多步骤表单）。
#### 二、面试高频问题
1. ​**为什么 `MVVM` 比 `MVC` 更优？​**​
    - 答：`MVVM` 通过数据绑定减少手动操作 `UI`，解耦更彻底，适合数据驱动场景。
2. ​**MVP 和 `MVI` 的区别？​**​
    - 答：MVP 依赖接口通信，Presenter 可能臃肿；`MVI` 强制单向流，状态集中管理，更适合复杂交互。
3. `​MVI` 如何解决状态膨胀？
    - 答：通过组合 State（如使用 `sealed class` 或 `@Immutable` 注解），按功能划分 State 模块。
4. ​**如何选择架构？​**​
    - 答：简单项目用 `MVC`；需测试用 MVP；数据驱动用 `MVVM`；复杂状态用 `MVI`。
