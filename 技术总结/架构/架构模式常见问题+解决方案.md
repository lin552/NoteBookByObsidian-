|架构模式|核心优势|典型问题|关键解决思路|
|---|---|---|---|
|MVC|简单易用，学习成本低|View 与 Controller 耦合|分离职责，使用接口抽象|
|MVP|职责清晰，测试友好|内存泄漏，接口膨胀|弱引用/生命周期解绑，拆分接口|
|MVVM|数据驱动，自动更新 UI|内存泄漏，数据倒灌|绑定生命周期，使用 SingleLiveEvent|
|MVI|单向流，状态可追溯|状态管理复杂，副作用处理|统一状态封装，独立副作用流|
#### 一、`MVC`
##### ①核心问题：
`MVC` 的经典结构是：`Model（数据）`→ `Controller（逻辑）`→ `View（展示）`，但在 Android 中常因职责边界模糊导致问题。
##### ②常见问题与解决：
###### 1.View与Controller耦合严重
- **表现**​：Activity/Fragment 同时承担 View（界面展示）和 Controller（事件处理、业务逻辑），导致代码臃肿（“上帝类”）。
- ​**原因**​：Android 的 Activity 天然绑定生命周期和界面，开发者习惯将逻辑写在 Activity 中，未严格分离职责。
- ​**解决**​：
    - 定义独立的 `Controller`类（非 Activity/Fragment），负责处理点击、网络请求等业务逻辑，View（Activity）仅负责渲染。
    - 使用 `Interface`抽象 View 行为（如 `IUserView`），Controller 持有 View 接口而非具体实现，降低耦合。
###### 2.测试困难
- **表现**​：View 与 Controller 强绑定，单元测试需启动 Activity 或依赖 Android 上下文，效率低。
- ​**原因**​：逻辑集中在 Activity 中，未通过接口抽象解耦。
- **解决**​：
    - 通过依赖注入（如 Hilt）将 Model 和 Controller 注入到 View，方便 Mock 测试。
    - 对 Controller 编写纯单元测试（无需 Android 环境），验证业务逻辑正确性。
###### 3.生命周期管理混乱
- ​**表现**​：网络请求、数据库操作等异步任务未与 Activity 生命周期绑定，导致 Activity 销毁后回调更新 `UI` 崩溃（如 `NullPointerException`）。
- **原因**​：未显式管理异步任务的生命周期，或未在 `onDestroy`中取消任务。
- ​**解决**​：
    - 使用 `Lifecycle`组件（如 `LifecycleScope`）启动协程，自动随生命周期取消。
    - 对 Retrofit 请求使用 `Call.cancel()`，或在 `onDestroy`中终止异步任务。

#### 二、`MVP`
##### ①核心问题：
MVP 通过 `Presenter`隔离 View 和 Model，View 仅负责展示，Presenter 处理所有逻辑。但 Android 中易因引用管理不当导致内存泄漏。
##### ②常见问题及解决
###### 1. ​**内存泄漏**​
- ​**表现**​：Activity 销毁后，Presenter 仍持有其强引用，导致 Activity 无法被回收。
- ​**原因**​：Presenter 通常直接持有 View（如 Activity）的实例，未感知生命周期。
- ​**解决**​：
    - 让 Presenter 持有 View 的**弱引用**​（`WeakReference<View>`），或在 View 销毁时（如 `onDestroy`）调用`Presenter.detachView()`主动解除引用。
    - 使用 `Lifecycle`组件，让 Presenter 监听 View 的生命周期（如 `LifecycleObserver`），在 `ON_DESTROY`时自动释放。
###### 2. ​**View 与 Presenter 接口膨胀**​
    - ​**表现**​：为满足各种交互需求，View 和 Presenter 接口需定义大量方法（如 `onButtonClick()`、`onDataLoaded()`），维护成本高。
    - ​**原因**​：过度设计接口，或未对相似功能进行分层。
    - ​**解决**​：
        - 按功能模块拆分接口（如 `UserView`、`OrderView`），避免单一接口包含所有方法。
        - 使用 Kotlin 扩展函数或委托模式简化重复代码。
###### 3. ​**Presenter 逻辑臃肿**​
- ​**表现**​：Presenter 承担过多职责（如网络请求、数据解析、业务规则），违反单一职责原则。
- **原因**​：未对复杂逻辑进一步拆分，或依赖底层组件（如直接操作数据库）。
- ​**解决**​：
    - 将数据处理、网络请求等逻辑下沉到独立的 `UseCase`或 `Repository`层，Presenter 仅负责协调。
    - 使用中介者模式（Mediator）管理多个子 Presenter，避免单个 Presenter 过于庞大。
#### 三、`MVVM`
##### ① 核心问题：
`MVVM` 通过 `ViewModel`管理数据，`LiveData`/`StateFlow`实现数据驱动 `UI`，但易因生命周期管理不当导致内存泄漏或数据倒灌。
##### ② 常见问题及解决：
###### 1.内存泄漏
- ​**表现**​：Activity 销毁后，`ViewModel` 仍通过 `LiveData`观察回调更新 `UI`，导致 Activity 无法回收。
- ​**原因**​：
    - 错误使用 `observeForever()`（未绑定生命周期）。
    - `ViewModel` 间接持有 View 引用（如通过回调接口）。
- ​**解决**​：
    - 始终使用 `LiveData.observe(owner, observer)`，绑定 Activity/Fragment 的生命周期（`LifecycleOwner`），自动在 `onDestroy`时移除观察者。
    - `ViewModel` 仅通过 `LiveData`传递数据，不持有 View 任何引用（包括弱引用）。
###### 2.数据倒灌（`Configuration Change 重复回调`）
- ​**表现**​：屏幕旋转等配置变更导致 Activity 重建，`ViewModel` 中旧数据被重新发送，`UI` 重复更新（如列表重复加载）。
- ​**原因**​：`LiveData`是粘性事件（Sticky Event），新观察者会收到最近一次的数据；配置变更后 View 重新订阅，触发重复回调。
- ​**解决**​：
    - 使用 `SingleLiveEvent`（自定义 `LiveData`，仅发送一次事件）。
    - 在观察时检查 View 状态（如 `if (isAdded())`），避免无效更新。
    - 使用 `StateFlow`替代 `LiveData`（配合 `repeatOnLifecycle`，仅在活跃生命周期接收数据）。
###### 3.数据绑定复杂性
- ​**表现**​：双向绑定（如 `EditText`与 `ViewModel`数据同步）可能导致循环更新或内存泄漏。
- ​**原因**​：未正确处理绑定生命周期，或数据变更触发多次回调。
- ​**解决**​：
    - 使用 Android 官方 `ViewDataBinding`，并在 `onDestroy`中调用 `binding.unbind()`释放资源。
    - 双向绑定使用 `@={viewModel.data}`语法，确保数据变更仅触发一次 `UI`更新（避免在 setter 中重复修改数据）。

#### 四、`MVI`
##### ① 核心问题：
`MVI` 强调**单向数据流**和**不可变状态**，通过 `Intent`（用户行为）→ `State`（`UI` 状态）→ `View`（渲染）的闭环管理，但易因状态管理复杂导致逻辑混乱。
##### ② 常见问题与解决：
###### 1. ​**状态管理混乱**​
- ​**表现**​：多个独立状态（如加载中、数据成功、错误）需合并处理，状态切换逻辑复杂，易遗漏边界条件。
- ​**原因**​：未统一封装状态，或状态类设计不合理（如平铺多个字段）。
- ​**解决**​：
	- 使用 `Sealed Class`定义统一状态（如 `UiState { data: T?, loading: Boolean, error: Throwable? }`），确保状态完整性。
    - 通过 `StateReducer`合并多个状态变更（如加载完成且无错误时更新数据）。
 ###### 2. ​**副作用（Side Effect）处理不当**​
- ​**表现**​：网络请求、Toast 提示等一次性操作（副作用）可能被重复触发（如快速点击按钮），或与 `UI` 状态绑定过紧。
- **原因**​：副作用未与 `UI` 状态解耦，或未限制其执行时机。
- ​**解决**​
     - 使用独立的 `Effect`类封装副作用（如 `ToastEffect(message: String)`），通过 `SharedFlow`单次发射（`replay=0`）。
    - 在 `ViewModel` 中使用 `flatMapLatest`或 `debounce`操作符过滤重复事件（如快速点击）。
###### 3. ​**样板代码过多**​
- **表现**​：需定义大量 `Intent`、`State`、`Effect`类，以及对应的处理逻辑，代码冗余。
- ​**原因**​：`MVI` 强制要求显式声明所有用户行为和状态，未利用工具简化。
- ​**解决**​：
    - 使用 Kotlin 扩展（如 `sealed class`嵌套）或代码生成工具（如 `MVIKotlin`）自动生成状态转换逻辑。
    - 结合 `Jetpack Compose`，通过 `remember`和 `mutableStateOf`简化状态管理。
