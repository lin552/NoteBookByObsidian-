在 Android 中，“加载图片”通常指将图片资源（如本地文件、资源文件、网络图片等）解析为 `Bitmap`对象并显示到界面的过程。由于图片可能占用大量内存（尤其是高分辨率图片），Android 对图片加载有严格的内存管理机制。以下是原生的图片加载方式、核心原理及优化策略：

#### 一、原生图片加载的核心方式
Android 加载图片的本质是通过 `BitmapFactory`类解析图片数据为 `Bitmap`对象，主要来源包括 ​**本地资源、本地文件、网络流**​ 三种场景。
##### 1.从本地资源加载（`res/drawable`）
通过 `Resources`和 `BitmapFactory`解析应用内的图片资源（如 `drawable`目录下的图片）：
```kotlin
// 从资源文件加载 Bitmap（如 res/drawable/ic_launcher.png）
val options = BitmapFactory.Options()
options.inSampleSize = 2 // 采样率（后续详细说明）
val bitmap = BitmapFactory.decodeResource(resources, R.drawable.ic_launcher, options)
imageView.setImageBitmap(bitmap)
```
##### 2.从本地文件加载（存储路径）
从内部存储、外部存储或 SD 卡的文件路径加载图片：
```kotlin
// 从内部存储文件加载
val imageFile = File(context.filesDir, "avatar.jpg")
val bitmap = BitmapFactory.decodeFile(imageFile.absolutePath)

// 从外部公共目录加载（需权限或通过 MediaStore 获取 Uri）
val publicImageFile = File(Environment.getExternalStoragePublicDirectory(Environment.DIRECTORY_PICTURES), "my_photo.jpg")
val bitmap = BitmapFactory.decodeFile(publicImageFile.absolutePath)
```

##### 3.从网络流加载（`HTTP/HTTPS`）
通过网络请求获取图片流后解析（需在子线程执行，避免阻塞主线程）：
```kotlin
// 使用 HttpURLConnection 下载网络图片（示例）
Thread {
    val url = URL("https://example.com/image.jpg")
    val connection = url.openConnection() as HttpURLConnection
    connection.connect()
    val inputStream = connection.inputStream
    // 解析流为 Bitmap
    val bitmap = BitmapFactory.decodeStream(inputStream)
    // 切回主线程更新 UI
    runOnUiThread {
        imageView.setImageBitmap(bitmap)
    }
}.start()
```

#### 二、Android图片加载的核心挑战：内存管理
图片的像素数据（如一张 `1920x1080` 的 `ARGB_8888` 格式图片）占用的内存约为 `1920 * 1080 * 4 ≈ 8MB`，而 Android 应用的堆内存（Heap Size）通常较小（如 `16MB~64MB`）。直接加载高分辨率图片会导致 ​**内存溢出（`OOM`）​**，因此 Android 提供了以下核心机制优化内存使用：
##### 1.采样率（`inSampleSize`）:降低图片分辨率
通过 `BitmapFactory.Options.inSampleSize`属性，按比例缩小图片的宽高，从而减少内存占用。
​**原理**​：`inSampleSize=2`表示宽高各缩小 2 倍，像素数变为原来的 1/4，内存占用降至 1/4。
**使用步骤：**
•先通过 `inJustDecodeBounds=true`仅解析图片尺寸（不加载内存）：
```kotlin
val options = BitmapFactory.Options().apply { inJustDecodeBounds = true }
BitmapFactory.decodeFile(imagePath, options) // 此时 options.outWidth/outHeight 为图片实际宽高
```
计算合适的 `inSampleSize`（通常取 2 的幂次）：
```kotlin
val reqWidth = 400 // 目标宽度（如 ImageView 的宽度）
val reqHeight = 300 // 目标高度
options.inSampleSize = calculateInSampleSize(options, reqWidth, reqHeight)

// 计算函数
fun calculateInSampleSize(options: BitmapFactory.Options, reqWidth: Int, reqHeight: Int): Int {
    val (height: Int, width: Int) = options.run { outHeight to outWidth }
    var inSampleSize = 1
    if (height > reqHeight || width > reqWidth) {
        val halfHeight: Int = height / 2
        val halfWidth: Int = width / 2
        while (halfHeight / inSampleSize >= reqHeight && halfWidth / inSampleSize >= reqWidth) {
            inSampleSize *= 2
        }
    }
    return inSampleSize
}
```
•最终加载缩小后的图片：
```kotlin
options.inJustDecodeBounds = false // 恢复为加载模式
val bitmap = BitmapFactory.decodeFile(imagePath, options)
```

##### 2.颜色模式（`inPreferredConfig`）：减少内存占用
`Bitmap.Config`定义了像素的颜色存储格式，默认 `ARGB_8888`（每个像素占 4 字节），可根据需求选择更节省内存的格式：
- `RGB_565`：每个像素占 2 字节（无透明通道），适合不透明的图片（如jpg）。
- `ARGB_4444`：已废弃（精度低，不推荐）。
- `ALPHA_8`：仅存储透明度（每个像素占 1 字节），适合黑白遮罩图。
**示例**​：
```kotlin
options.inPreferredConfig = Bitmap.Config.RGB_565 // 加载 jpg 时节省 50% 内存
```

##### 3.复用内存（`inBitmap`）：避免重复分配
Android 3.0（API 11）起支持 `inBitmap`属性，允许复用已存在的 `Bitmap`内存空间（需满足尺寸和配置兼容），减少 `GC` 压力。
**使用条件**​：
- Android 3.0~4.3（API 11~18）：新 `Bitmap`的宽高必须 ≤ 原 `Bitmap`的宽高，且配置相同。
- Android 4.4+（API 19+）：新 `Bitmap`的总像素数 ≤ 原 `Bitmap`的总像素数，配置可不同（如原 `ARGB_8888`，新 `RGB_565`）。
**示例：**
```kotlin
// 复用已有的 Bitmap 内存（假设 oldBitmap 已不再使用）
val oldBitmap = ... // 已加载的 Bitmap
val options = BitmapFactory.Options().apply {
    inSampleSize = 2
    inBitmap = oldBitmap // 复用其内存
}
val newBitmap = BitmapFactory.decodeFile(imagePath, options)
```

#### 三、原生图片加载的完整流程
Android 加载图片的核心流程可分为 ​**解码、内存分配、渲染**​ 三个阶段：

##### 1.解码阶段（Decoding）
通过 `BitmapFactory.decodeXXX()`方法读取图片原始数据（如 `PNG/JPG` 的字节流），解析图片的宽高、颜色模式等元信息（`inJustDecodeBounds=true`时仅解析元信息）。

##### 2.内存分配阶段（Memory Allocation）​
根据解析的元信息和 `BitmapFactory.Options`（如 `inSampleSize`、`inPreferredConfig`），计算实际需要的像素数据大小，并向系统申请内存。若内存不足，触发 `GC` 或抛出 `OOM`。

##### 3.渲染阶段（Rendering）
将解码后的像素数据填充到 `Bitmap`对象中，并通过 `ImageView.setImageBitmap()`将 `Bitmap`绘制到界面（最终由 GPU 渲染到屏幕）。

#### 四、原生图片加载的优化策略
为了高效加载图片（尤其是列表场景），原生开发中需结合以下策略：
##### 1.异步加载（避免主线程阻塞）
图片解码（尤其是大图片或网络图片）是耗时操作，必须在子线程执行。原生可使用：
- ​**Handler + Thread**​：通过 `Handler`将结果发送到主线程更新 `UI`。
- ​`AsyncTask`**​（已弃用）：适用于简单的后台任务（Android 11 已移除）。
- ​**Kotlin 协程**​：通过 `CoroutineScope(Dispatchers.IO)`执行后台任务，`withContext(Dispatchers.Main)`切回主线程。
- `​ExecutorService`​：使用线程池管理后台线程（推荐）。
##### 2.三级缓存（减少重复加载）
原生开发中可手动实现三级缓存（内存缓存 + 磁盘缓存 + 网络），提升加载效率：
•**内存缓存（`LruCache`）​**​：使用 `LruCache<String, Bitmap>`缓存最近使用的图片（基于 `LRU` 算法淘汰旧数据）。
```kotlin
// 初始化内存缓存（建议大小为可用内存的 1/8）
val maxMemory = (Runtime.getRuntime().maxMemory() / 1024).toInt()
val cacheSize = maxMemory / 8
val memoryCache = object : LruCache<String, Bitmap>(cacheSize) {
    override fun sizeOf(key: String, bitmap: Bitmap): Int {
        return bitmap.byteCount / 1024 // 单位 KB
    }
}
```
•**磁盘缓存（`DiskLruCache`）​**​：使用 `DiskLruCache`缓存到本地存储（需处理文件读写和 IO 异常）。
```kotlin
// 初始化磁盘缓存（需在后台线程创建）
val diskCacheDir = File(context.cacheDir, "bitmap_cache")
if (!diskCacheDir.exists()) diskCacheDir.mkdirs()
val diskLruCache = DiskLruCache.open(diskCacheDir, 1, 1, 10 * 1024 * 1024) // 10MB 缓存大小
```

##### 3.列表图片加载优化（`RecyclerView/ListView`）
- **复用 ImageView**​：通过 `onBindViewHolder`复用 `ImageView`，避免重复创建。
- ​**占位图**​：加载过程中显示默认占位图，提升用户体验。
- ​**取消无效请求**​：当 `ImageView`被滑出屏幕时，取消对应的加载任务（避免加载到错误的图片）。
#### 五、原生方式的局限性与第三方库的选择
原生图片加载需要手动处理 ​**内存管理、异步加载、三级缓存、列表优化**​ 等复杂逻辑，开发成本高且容易出错。因此，实际项目中更推荐使用成熟的第三方库（如 Glide、Coil、Picasso），它们封装了上述所有优化，同时支持更多高级功能（如图片变换、动画、预加载等）。
