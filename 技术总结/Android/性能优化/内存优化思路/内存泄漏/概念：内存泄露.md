Android 内存泄漏（Memory Leak）是指**对象不再被使用，但由于被意外引用而无法被垃圾回收（`GC`）​，导致内存无法释放的现象。长期积累可能导致内存溢出（`OOM`），影响应用性能。以下是 Android 内存泄漏的核心考点及详细解析：

#### 一、内存泄漏的核心原因
对象被**长生命周期的对象**​（如静态变量、单例、Application 上下文）​**强引用**，且这些长生命周期对象不会被 `GC` 回收，导致被引用的短生命周期对象（如 Activity、Fragment）无法被 `GC`。
#### 二、Android中常见的内存泄漏场景
##### 1.Activity/Fragment泄漏（最核心的场景）
Activity 和 Fragment 的生命周期受系统控制（如旋转屏幕、返回键），若被长生命周期对象错误引用，会导致泄漏。
**典型示例：​**​
- ​**非静态内部类/匿名内部类持有 Activity 引用**​  
    匿名内部类（如 `Handler`、`Runnable`、点击监听器）会隐式持有外部 Activity 的引用。若其在 Activity 销毁后仍存活（如延迟任务未执行完），会导致 Activity 无法回收。
```java
// 错误示例：匿名 Handler 持有 Activity 引用
public class MainActivity extends Activity {
    private Handler mHandler = new Handler() {
        @Override
        public void handleMessage(Message msg) {
            // 处理消息（此时 Activity 可能已销毁）
        }
    };

    @Override
    protected void onCreate(Bundle savedInstanceState) {
        super.onCreate(savedInstanceState);
        mHandler.postDelayed(() -> {}, 10000); // 延迟 10s 执行，若 Activity 销毁前未移除，会泄漏
    }
}
```
- ​**静态变量/单例持有 Activity 引用**​  
    静态变量的生命周期与应用一致，若直接赋值为 Activity 实例（如 `static Context sContext = this`），会导致 Activity 无法回收。  
    单例模式中若传入 Activity 上下文（而非 Application 上下文），同样会泄漏。
    
- ​**异步任务未取消**​  
    `AsyncTask`、`Thread` 或 `RxJava` 订阅若在 Activity 销毁后未终止，且持有 Activity 引用，会导致泄漏。例如：
```java
// 错误示例：AsyncTask 未取消
public class MainActivity extends Activity {
    private MyAsyncTask mTask;

    @Override
    protected void onCreate(Bundle savedInstanceState) {
        super.onCreate(savedInstanceState);
        mTask = new MyAsyncTask(this).execute();
    }

    class MyAsyncTask extends AsyncTask<Void, Void, Void> {
        private WeakReference<MainActivity> mActivityRef;

        MyAsyncTask(MainActivity activity) {
            mActivityRef = new WeakReference<>(activity);
        }

        @Override
        protected Void doInBackground(Void... voids) {
            // 耗时操作
            return null;
        }
    }
}
```
#####  2.资源未正确释放​
未显式释放的资源可能长期占用内存，间接导致泄漏：
- ​**Bitmap 未回收**​：未调用 `bitmap.recycle()`（API 30 后已废弃，需通过 `setImageBitmap(null)` 释放）。
- ​**Cursor/数据库连接未关闭**​：`Cursor` 未调用 `close()`，或 `SQLiteDatabase` 连接未释放。
- ​**IO 流未关闭**​：`FileInputStream`、`Socket` 等未在 `finally` 块中关闭。
##### ​3. 监听器/回调未移除​
注册的监听器（如广播接收器、事件总线、`ContentObserver`）若未在生命周期结束时反注册，会持有 Activity/Fragment 引用：
- ​**广播接收器**​：动态注册的 `BroadcastReceiver` 未调用 `unregisterReceiver()`。
- ​**事件总线**​：`EventBus`、`RxBus` 等未调用 `unregister()` 取消订阅。
- ​**数据库观察者**​：`ContentResolver.registerContentObserver()` 未反注册。
##### 4. 集合类持有对象​
全局静态集合（如 `static List<Object>`）若未及时清理，会持续持有对象引用。例如：
```java
// 错误示例：静态集合未清理
public class Utils {
    private static List<Activity> sActivityList = new ArrayList<>();

    public static void addActivity(Activity activity) {
        sActivityList.add(activity);
    }
}

// Activity 未从 sActivityList 移除时，即使销毁也无法回收
```
##### 5. `WebView` 特殊泄漏**​
`WebView` 内部可能持有 Activity 引用，需严格按规范销毁：
```java
// 正确销毁 WebView
webView.stopLoading();
webView.removeAllViews();
webView.destroy();
webView = null; // 避免被静态变量引用
```
##### 6. 第三方库泄漏​
部分第三方库（如图片加载库 Glide、网络请求库 `OkHttp`）若未正确释放资源，可能导致泄漏。需遵循官方文档，在生命周期中释放（如 `Glide.with(activity).clear(imageView)`）。

#### 三、内存泄漏的检测工具
- ​`LeakCanary`​：Square 开发的自动化泄漏检测工具，通过监听 Activity/Fragment 的生命周期，自动检测泄漏并生成堆转储（Heap Dump）。
- ​`Android Studio Profiler`：通过 `Memory Profiler` 实时监控内存使用，手动触发 `GC` 后对比对象数量，定位泄漏。
- ​**Heap Dump 分析**​：通过 Android Studio 的 `Dump Java Heap` 功能，使用 `OQL`（类似 SQL）查询未被回收的对象及其引用链。

#### 四、内存泄漏的解决方案
针对不同场景，采取以下策略：
##### **1. 避免 Activity/Fragment 被长生命周期对象引用**​
- ​**使用静态内部类 + 弱引用**​：Handler、`Runnable` 等内部类改为静态，通过 `WeakReference` 持有 Activity 引用，并在 `onDestroy` 中移除未处理的消息。
```java
// 正确示例：静态 Handler + 弱引用
public class MainActivity extends Activity {
    private MyHandler mHandler = new MyHandler(this);

    static class MyHandler extends Handler {
        private WeakReference<MainActivity> mActivityRef;

        MyHandler(MainActivity activity) {
            mActivityRef = new WeakReference<>(activity);
        }

        @Override
        public void handleMessage(Message msg) {
            MainActivity activity = mActivityRef.get();
            if (activity != null && !activity.isFinishing()) {
                // 处理消息
            }
        }
    }

    @Override
    protected void onDestroy() {
        super.onDestroy();
        mHandler.removeCallbacksAndMessages(null); // 移除所有消息
    }
}
```
- **使用 Application 上下文**​：单例或静态变量需上下文时，优先使用 `getApplicationContext()`。
- ​**及时取消异步任务**​：在 `onDestroy` 中调用 `AsyncTask.cancel(true)`、`RxJava` 的 `Disposable.dispose()` 或取消线程。
##### **2. 释放资源**​
- Bitmap：通过 `imageView.setImageBitmap(null)` 释放，或使用 `Glide` 等库自动管理。
- Cursor：使用 `try-with-resources`（API 26+）或在 `finally` 中调用 `cursor.close()`。
- 流/连接：确保在 `finally` 块中关闭 `InputStream`、`OutputStream`、`Socket` 等。
##### ​3. 移除监听器/回调​
- 广播接收器：动态注册的 `BroadcastReceiver` 在 `onDestroy` 中调用 `unregisterReceiver()`。
- 事件总线：在 `onDestroy` 中调用 `EventBus.getDefault().unregister(this)`。
- 数据库观察者：反注册 `ContentObserver`（`contentResolver.unregisterContentObserver(observer)`）。
##### ​4. 清理集合类​
静态集合需在使用后调用 `clear()`，或改用弱引用集合（如 `WeakHashMap`）。
##### ​**5. 规范 `WebView` 使用**​
严格按生命周期销毁 `WebView`，避免静态变量持有 `WebView` 实例。
