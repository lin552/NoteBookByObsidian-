Java `ConcurrentHashMap` 是线程安全的哈希表实现，专为高并发场景设计。其核心考点围绕**线程安全机制**、**底层数据结构**、**并发优化策略**及`JDK` 版本差异**展开。以下是详细梳理：

#### 一、底层数据结构（`JDK7` vs `JDK8`）
`ConcurrentHashMap` 在不同 `JDK` 版本中底层结构差异显著，核心优化方向是**降低锁粒度**和**提升并发效率**。
##### 1)`JDK 7` 及之前：Segment 数组 + `HashEntry` 数组 + 链表**​
- ​`Segment`**​：继承自 `ReentrantLock`，每个 `Segment` 独立加锁，相当于一个“子哈希表”。默认有 16 个 `Segment`（并发级别），每个 `Segment` 包含一个 `HashEntry` 数组（默认容量 2，可扩容）。
- ​`HashEntry​`：链表节点，存储键值对，通过 `next` 指针连接。
- ​**特点**​：通过分段锁（`Segment`）减少锁竞争，同一时间仅一个 `Segment` 加锁，其他 `Segment` 可并行操作。但 `Segment` 数量固定（默认 16），并发度受限于此。
##### ​2) `JDK 8` 及之后：Node 数组 + 链表 + 红黑树（无 Segment）​**​
- ​**Node**​：替代 `HashEntry`，链表节点，存储键值对，`next` 指针指向后续节点。
- ​**红黑树**​：当链表长度 ≥ 8 且数组长度 ≥ 64 时，链表转换为红黑树（与 `JDK 8` `HashMap` 一致），提升查询效率。
- ​**树化与退化**​：红黑树节点数 ≤ 6 时退化为链表（减少树结构维护开销）。
- ​**特点**​：放弃 `Segment`，改用 `CAS + synchronized` 实现细粒度锁（仅锁定链表/红黑树的头节点），并发效率更高。

#### 二、线程安全机制
`ConcurrentHashMap` 通过以下机制保证线程安全：
##### **1） `JDK` 7：分段锁（Segment）​**​
- 每个 `Segment` 继承 `ReentrantLock`，内部维护 `HashEntry` 数组。
- 操作（如 `put`）时，先锁定对应的 `Segment`，再操作其内部的 `HashEntry` 数组。
- ​**优点**​：锁粒度为 `Segment`（默认 16 个），并发度高；
- ​**缺点**​：`Segment` 数量固定，并发度受限于初始配置；`Segment` 内存占用较高（每个 `Segment` 独立锁对象）。
##### ​**2) `JDK8`：`CAS` + `synchronized`（细粒度锁）​**​
- ​`CAS`（无锁编程）​**​：用于节点的插入和扩容，通过 `compareAndSwap` 原子操作保证原子性，避免传统锁的开销。
- ​**synchronized（轻量级锁）​**​：仅锁定链表或红黑树的**头节点**​（`JDK 8` 中头节点作为锁对象），其他节点无需加锁。例如，多个线程同时插入同一桶时，仅第一个获取头节点锁的线程执行插入，后续线程等待锁释放后继续。
- ​**优点**​：锁粒度更小（仅头节点），并发效率更高；无需预分配固定数量的锁（`Segment`）。
#### 三、关键操作流程
##### **1） put() 方法流程（`JDK 8`）​**​
1. ​**计算哈希值**​：与 `HashMap` 类似，通过 `(h = key.hashCode()) ^ (h >>> 16)` 混合高位信息，减少哈希冲突。
2. ​**确定桶位置**​：通过 `hash & (n - 1)`（`n` 为数组长度，2 的幂次）计算桶索引。
3. ​**初始化数组（懒加载）​**​：若数组未初始化（`table == null`），通过 `initTable()` 初始化（`CAS` 保证原子性）。
4. ​**插入或更新节点**​：
    - ​**无锁竞争**​：通过 `CAS` 尝试插入新节点（`Node`）到桶的头部。若成功，结束；若失败（说明有其他线程已修改），进入同步逻辑。
    - ​**同步控制**​：对桶的头节点加 `synchronized` 锁，遍历链表/红黑树：
        - 若找到相同 `key`（`equals` 判断），更新值；
        - 若未找到，插入到链表尾部（或红黑树中）。
5. ​**树化判断**​：若链表长度 ≥ 8 且数组长度 ≥ 64，将链表转换为红黑树；若红黑树节点数 ≤ 6，退化为链表。
6. ​**扩容检查**​：若元素数量超过阈值（`size > threshold`），触发扩容（`tryPresize()`）。
##### ​**2) get() 方法流程**​
- ​**无锁读取**​：直接遍历桶中的链表或红黑树（`JDK 8` 红黑树节点增加了 `val` 和 `next` 的 volatile 修饰，保证可见性），通过 `equals` 匹配 `key`，返回对应值（若存在）。
- ​**可见性保证**​：`Node` 的 `val` 和 `next` 字段均用 `volatile` 修饰，确保多线程下的可见性。
##### ​**3) 扩容机制（`JDK 8`）​**​
- ​**触发条件**​：元素数量超过 `capacity * loadFactor`（默认负载因子 0.75）。
- ​**扩容方式**​：容量翻倍（如 16 → 32），创建新数组，将旧数组元素重新哈希到新数组。
- ​**并发扩容优化**​：
    - ​`ForwardingNode`**​：标记已迁移的桶（替换原桶的头节点），其他线程访问到 `ForwardingNode` 时会参与扩容（协助迁移）。
    - ​**多线程协作**​：通过 `CAS` 将旧数组元素分批迁移到新数组（每次迁移一个 `sizeCtl` 控制的步长），减少单线程扩容耗时。
#### 四、`JDK7` vs `JDK8`核心差异
|​**特性**​|​**JDK 7**​|​**JDK 8**​|
|---|---|---|
|底层结构|Segment 数组 + HashEntry 数组 + 链表|Node 数组 + 链表 + 红黑树|
|线程安全机制|分段锁（Segment 继承 ReentrantLock）|CAS + synchronized（头节点锁）|
|锁粒度|Segment（默认 16 个）|链表/红黑树的头节点（更细粒度）|
|初始化时机|构造时初始化 Segment 数组|懒加载（首次 put 时初始化数组）|
|扩容协作|单线程扩容|多线程协作（ForwardingNode 标记）|
|红黑树支持|无|有（链表长度 ≥ 8 且数组 ≥ 64 时树化）|
#### 五、常见特性与细节
1. ​**不允许 `null` 键/值**​：`HashMap` 允许 `null` 键（存入 0 号桶），但 `ConcurrentHashMap` 不允许（`put(null, value)` 会抛出 `NullPointerException`）。
2. ​**弱一致性计数**​：`size()` 方法返回的是近似值（通过 `baseCount` 和 `CounterCell[]` 数组实现分段计数，减少竞争），而非精确值（类似 `AtomicInteger` 的 `CAS` 计数）。
3. ​**并发级别（Concurrency Level）​**​：`JDK 7` 中表示 `Segment` 的数量（默认 16），`JDK 8` 中仅作为初始数组大小的参考（实际数组大小为大于等于该值的 2 的幂次）。
4. ​**树化的额外条件**​：除链表长度 ≥ 8 外，还需数组长度 ≥ 64（避免哈希冲突过于集中时的误树化）。
#### 六、常见面试题
1. ​**`ConcurrentHashMap` 如何保证线程安全？`JDK 7` 和 `JDK 8` 的实现有何不同？​**​  
    `JDK 7` 使用分段锁（`Segment` 继承 `ReentrantLock`），每个 `Segment` 独立加锁；`JDK 8` 放弃 `Segment`，改用 `CAS` 无锁插入和 `synchronized` 锁定头节点，锁粒度更小，性能更高。
    
2. `​JDK 8` 为什么用 `synchronized` 而不是继续用分段锁？​**​  
    `synchronized` 经过 `JVM` 优化（偏向锁、轻量级锁），性能已接近 `ReentrantLock`；且分段锁的 `Segment` 数量固定，并发度受限，而 `synchronized` 锁粒度更细（仅头节点），并发效率更高。
    
3. ​**`ConcurrentHashMap` 的 `put` 方法中，`CAS` 失败后会怎样？​**​  
    `CAS`插入失败说明有其他线程已修改当前桶，此时会升级为对头节点的 `synchronized` 加锁，保证同一桶的原子性操作。
    
4. ​**`ConcurrentHashMap` 允许 `null` 键或值吗？为什么？​**​  
    不允许。`HashMap` 允许 `null` 键（哈希值为 0），但 `ConcurrentHashMap` 的 `putVal` 方法中若 `key` 或 `value` 为 `null` 会直接抛出 `NPE`（避免多线程下的空指针歧义）。
    
5. ​**`ConcurrentHashMap` 的 `size()` 方法为什么是弱一致性的？​**​  
    为了提升并发性能，`size()` 通过分段计数（`baseCount` 和 `CounterCell[]`）实现，允许短暂的数据不一致，但最终会收敛到准确值（类似 `AtomicLong` 的实现）。
    
6. ​`JDK 8` 扩容时如何利用多线程？​**​  
    通过 `ForwardingNode` 标记已迁移的桶，其他线程访问到该节点时会参与扩容（协助迁移），将旧数组元素分批迁移到新数组，减少单线程扩容耗时。
