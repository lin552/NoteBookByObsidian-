在 Android 系统中，​`OOM`（Out Of Memory）的触发与虚拟内存和真实内存均相关**，但具体表现和触发条件取决于内存管理机制和场景。以下是详细分析：

#### 一、Android 内存管理基础

1. **虚拟内存（Virtual Memory）​**​
    - ​**定义**​：每个应用进程拥有独立的虚拟地址空间（32 位系统为 `3GB`，64 位系统极大），由操作系统映射到物理内存（RAM）或磁盘交换空间（Swap）。
    - ​**特点**​：
        - 应用仅操作虚拟内存，物理内存由 OS 动态分配。
        - 虚拟内存允许预分配大块地址空间（如 `malloc` 或 `mmap`），但实际物理内存按需加载。
2. ​**真实内存（Physical Memory）​**​
    - ​**定义**​：设备实际物理内存（RAM），由所有进程共享。
    - ​**限制**​：容量有限（如 `4GB`、`8GB`），直接影响系统性能。

#### 二、`OOM`的触发条件
Android 的 `OOM` 本质是 ​**虚拟内存无法映射到可用物理内存或交换空间**，具体分为两种场景：
##### 1.**物理内存不足型 `OOM`
- ​**触发条件**​：物理内存 + 交换空间（Swap）耗尽，且无法回收更多内存。
- ​**典型场景**​：
    - 加载超大图片（如未压缩的 `4K` 图片）导致 Native 内存激增。
    - 频繁创建大对象（如 `Bitmap`、`byte[]`）且未及时回收。
- ​**日志特征**​：
```log
java.lang.OutOfMemoryError: Failed to allocate a X byte allocation with X free bytes and XMB until OOM
```

##### 2.​虚拟内存耗尽型 `OOM`
- **触发条件**​：进程申请的虚拟地址空间超过系统限制（如 32 位进程的 `3GB` 虚拟地址空间耗尽）。
- ​**典型场景**​：
    - 32 位应用频繁申请大块内存（如 `mmap` 映射大文件）。
    - 内存碎片化导致无法分配连续虚拟地址空间。
- ​**日志特征**​：
```log
Fatal signal 11 (SIGSEGV), code 1 (SEGV_MAPERR), fault addr 0xdeadbeef in tid XXXX (main)
```

#### 三、Android中`OOM`的常见原因与定位
##### 1. ​物理内存不足型 `OOM`
|原因|示例场景|工具定位方法|
|---|---|---|
|​**Bitmap 未回收**​|大量未释放的高分辨率图片|`Android Profiler` 监控 Native 内存|
|​**Native 内存泄漏**​|JNI 代码未释放 `malloc` 分配的内存|`adb shell dumpsys meminfo`|
|​**线程数过多**​|频繁创建未销毁的线程|`adb shell ps|

##### 2. ​**虚拟内存耗尽型 `OOM`

|原因|示例场景|工具定位方法|
|---|---|---|
|​**32 位地址空间不足**​|多个 `mmap` 映射大文件|`cat /proc/<pid>/maps`|
|​**内存碎片化**​|频繁分配/释放小对象导致碎片|`valgrind --tool=massif`|
|​**大对象预分配**​|静态变量预留超大内存池|`adb shell cat /proc/<pid>/status`|
#### 四、优化策略
##### ​1.物理内存优化**​
- ​**Bitmap 管理**​：
    - 使用 `BitmapFactory.Options.inSampleSize` 缩放图片。
    - 通过 `LruCache` 限制缓存大小。
- ​**Native 内存控制**​：
    - 及时调用 `munmap()` 释放 `mmap` 映射。
    - 使用 `AddressSanitizer` 检测内存泄漏。

##### 2. ​虚拟内存优化**​
- ​**避免 32 位地址空间耗尽**​：
    - 升级到 64 位进程（虚拟地址空间极大）。
    - 分批加载大资源（如分块读取文件）。
- ​**减少内存碎片**​：
    - 使用内存池（Memory Pool）管理小对象。
    - 合并频繁分配/释放的内存块。

#### 五、工具与日志分析
1. ​`Logcat` 日志**​：
    - 搜索 `OutOfMemoryError` 定位崩溃点。
    - 关注 `dalvik.vm.heapgrowthlimit` 和 `dalvik.vm.heapsize` 参数。
2. ​`Android Profiler`**​：
    - 监控 Java 堆（Java Heap）和 Native 堆（Native Heap）内存趋势。
    - 使用 ​**Allocation Tracking**​ 定位高频分配对象。
3. ​**Native 内存分析**​：
    - `adb shell dumpsys meminfo <pid>`：查看进程内存映射。
    - `pmap -x <pid>`：分析虚拟内存分布。
