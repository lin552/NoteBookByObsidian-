Java 中的 `synchronized` 是实现线程同步的核心关键字，用于保证多线程环境下共享资源的互斥访问。其考点覆盖**底层原理**、**锁优化**、**锁类型**、**特性与局限性**及**与其他锁的对比**等。以下是详细梳理：

#### 一、核心作用与基本用法
`synchronized` 用于修饰方法或代码块，确保同一时间只有一个线程执行被修饰的代码（互斥），并保证可见性（通过 `Monitor` 锁的释放-获取机制刷新变量到主内存）。
##### **1)修饰实例方法**​
锁是当前实例对象（`this`），同一实例的不同线程访问该方法时互斥。
```java
public synchronized void instanceMethod() {
   
}
```
##### ​**2) 修饰静态方法**​
锁是类的 `Class` 对象（如 `MyClass.class`），同一类的所有实例线程访问该方法时互斥。
```java
public static synchronized void staticMethod(){

}
```
##### ​**3)修饰代码块**​
显式指定锁对象（可以是任意 `Object`），灵活性更高。
```java
public void method(){
   Object lock = new Object();
   synchronized(lock){
   }
}
```
#### 二、底层实现原理
`synchronized` 的底层通过 ​`JVM` 的 Monitor 锁**实现，依赖操作系统提供的互斥量（`Mutex`）。核心流程涉及 `monitorenter` 和 `monitorexit` 指令。
##### 1) Monitor 锁（监视器锁）​**​
每个 Java 对象（包括数组）在 `JVM` 中对应一个 `Monitor` 对象（存储在对象头的 `Mark Word` 中），用于控制多线程对临界资源的访问。
- ​**`monitorenter`**​：线程进入同步代码块时，尝试获取对象的 `Monitor` 锁。若锁未被占用（计数器为 0），则获取锁并将计数器置为 1；若已被当前线程持有（可重入），则计数器加 1。
- ​**`monitorexit`**​：线程退出同步代码块时，释放 `Monitor` 锁（计数器减 1）；若计数器归零，锁被释放，其他线程可竞争获取。
#### 三、锁的优化：从重量级锁到轻量级锁
早期 `synchronized` 被称为“重量级锁”，因获取锁需向操作系统申请互斥量，上下文切换开销大。`JDK 6` 后引入**锁升级机制**​（偏向锁→轻量级锁→重量级锁），逐步优化性能。
##### 1) 偏向锁（Biased Locking）​​
- ​**目的**​：消除无竞争场景下的同步开销（适用于单线程重复访问同一锁的场景）。
- ​**原理**​：锁首次被线程获取时，记录该线程 ID（“偏向”该线程）。后续该线程访问时无需原子操作，直接进入同步块（计数器为 1）；若其他线程尝试获取，偏向模式失效，升级为轻量级锁。
- ​**适用场景**​：单线程或线程交替执行但无竞争的场景（如方法调用链固定）。
- ​**废弃**​：`JDK 15` 后默认禁用（`-XX:-UseBiasedLocking`），因维护偏向状态的额外开销在多线程场景下可能超过收益。
##### ​2. 轻量级锁（Lightweight Locking）​​
- ​**目的**​：减少多线程轻度竞争时的开销（通过 `CAS` 替代操作系统互斥量）。
- ​**原理**​：
    1. 线程通过 `CAS` 尝试将锁对象的 `Mark Word` 替换为指向自己栈中锁记录（`Lock Record`）的指针。
    2. 若替换成功（`CAS` 成功），获取轻量级锁；若失败（其他线程竞争），则膨胀为重量级锁。
- ​**适用场景**​：多线程轻度竞争（竞争次数少、持有锁时间短）。
##### ​**3. 重量级锁（Heavyweight Locking）​**​
- ​**目的**​：处理多线程高度竞争场景（`CAS`失败次数超过阈值）。
- ​**原理**​：锁对象的 `Mark Word` 指向操作系统互斥量（`Mutex`），线程通过操作系统内核进行阻塞/唤醒（上下文切换开销大）。
#### 四、关键特性
##### ​1)可重入性（`Reentrancy`）​​
同一线程可多次获取同一把锁（计数器递增），避免自身死锁。例如：
```java
public synchronized void outer() {
    inner(); // 内部调用同样被 synchronized 修饰的方法
}

public synchronized void inner() { ... }
```

- ​**实现**​：通过 `Monitor` 锁的计数器（`entryCount`）实现，当前线程获取锁时计数器加 1，释放时减 1（计数器归零时释放锁）。
##### ​2)不可中断性​
一旦线程获取锁，其他线程必须等待锁释放（无法通过 `interrupt()` 中断等待）。与 `ReentrantLock.tryLock(long timeout, TimeUnit unit)` 或 `lockInterruptibly()` 不同。
##### ​3)非公平性​
锁的获取不保证先到先得（默认非公平）。线程竞争锁时，`JVM` 不保证等待时间最长的线程优先获取，可能导致“饥饿”现象（但减少了上下文切换开销）。

#### 五、与其他锁的对比
##### 1. `synchronized` vs `ReentrantLock`
|​**特性**​|​**synchronized**​|​**ReentrantLock**​|
|---|---|---|
|锁类型|JVM 层面实现（Monitor）|JDK 层面实现（基于 AQS）|
|灵活性|固定（非公平、不可中断、无超时）|可配置（公平/非公平、可中断、尝试锁）|
|性能|早期差（重量级锁），优化后接近|早期优（CAS），后期接近|
|条件变量|仅一个等待队列（`wait/notify`）|支持多个条件队列（`Condition`）|
|使用场景|简单同步需求|复杂同步（如限时获取、公平锁）|
#### 2. `synchronized` vs `volatile`
- `volatile` 保证可见性和禁止指令重排，但不保证原子性（如 `i++` 需配合 `synchronized` 或 `AtomicXXX`）。
- `synchronized` 保证原子性、可见性、有序性（通过 `Monitor` 锁的释放-获取机制）。
#### 六、常见面试题
1. ​`synchronized` 的底层原理是什么？​**​  
    基于 `JVM` 的 Monitor 锁，通过 `monitorenter` 和 `monitorexit` 指令实现。锁对象的对象头 `Mark Word` 存储 Monitor 锁的状态（偏向、轻量级、重量级）。
    
2. ​**锁的升级过程是怎样的？为什么需要升级？​**​  
    升级顺序：偏向锁→轻量级锁→重量级锁。目的是在不同竞争场景下减少开销：无竞争时用偏向锁，轻度竞争用轻量级锁（`CAS`），高度竞争时用重量级锁（内核互斥）。
    
3. ​**偏向锁为什么被废弃？​**​  
    维护偏向状态的额外开销（如记录线程 ID、检查偏向线程）在多线程场景下可能超过收益，`JDK 15` 后cc默认禁用。
    
4. ​`synchronized` 修饰静态方法和实例方法的锁对象分别是什么？​**​  
    静态方法锁是类的 `Class` 对象（如 `MyClass.class`）；实例方法锁是当前实例对象（`this`）。
    
5. ​`synchronized` 是可重入的吗？为什么？​**​  
    是。通过 `Monitor` 锁的计数器实现，当前线程多次获取同一锁时计数器递增，释放时递减，避免死锁。
    
6. ​`synchronized` 和 `ReentrantLock` 的主要区别是什么？​**​  
    灵活性（`ReentrantLock` 支持公平锁、可中断、尝试锁）、性能（后期接近）、条件变量（`ReentrantLock` 支持多个 `Condition`）。
    
7. ​**`synchronized` 能否保证可见性？如何保证？​**​  
    能。线程释放锁时，会将共享变量的最新值刷新到主内存；获取锁时，从主内存读取最新值（通过 `Monitor` 锁的释放-获取语义）。
