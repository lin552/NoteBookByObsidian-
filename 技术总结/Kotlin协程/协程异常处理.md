#### 一、协程异常处理的核心方式

协程中的异常分为两种：​**可捕获的异常**​（通过 `try-catch`处理）和**未捕获的异常**​（会导致协程取消并向上传播）。以下是常见处理方式：

##### 1.直接使用 try-catch 包裹协程体
在协程内部（如 `launch`或 `async`的 lambda 中）使用 `try-catch`捕获异常，适用于**预期内的异常**​（如网络请求失败）。
```kotlin
viewModelScope.launch {
    try {
        val result = fetchData() // 可能抛出异常的挂起函数
        updateUI(result)
    } catch (e: Exception) {
        // 处理异常（如显示错误提示）
        showError(e.message)
    }
}
```

##### 2.使用`CoroutineExceptionHandler` 全局捕获未处理异常
对于未被协程内部捕获的异常，可通过 `CoroutineExceptionHandler`全局监听（类似 `Thread.UncaughtExceptionHandler`）。
**注意**​：它仅在协程**未被父作用域捕获异常**时触发，且通常用于根协程（如 `viewModelScope`或自定义顶层作用域）。
```kotlin
val exceptionHandler = CoroutineExceptionHandler { _, e ->
    Log.e("CoroutineError", "Unhandled exception: $e")
}

// 根协程使用异常处理器
viewModelScope.launch(exceptionHandler) {
    throw RuntimeException("Oops!") // 未被内部捕获，触发 exceptionHandler
}
```

##### 3.`supervisorScope`：子协程异常隔离
默认情况下，父协程的一个子协程异常会导致整个父协程及所有兄弟子协程取消（类似“一荣俱荣，一损俱损”）。
若需实现“子协程异常互不影响”（类似 Android 中 `SupervisorJob`），可使用 `supervisorScope`：
```kotlin
viewModelScope.launch {
    supervisorScope { // 子协程异常不会传播到父协程
        launch { task1() } // 若 task1 抛异常，仅自身取消
        launch { task2() } // task2 仍会正常执行
    }
}
```

##### 4.`async`的特殊处理：异常延迟抛出
`async`启动的协程不会立即抛出异常，而是将异常封装在 `Deferred`对象中，直到调用 `await()`时才会抛出。
因此，`async`内部的异常需在 `await()`处捕获：
```kotlin
viewModelScope.launch {
    val deferred = async { fetchData() } // 异常未抛出
    try {
        val result = deferred.await() // 此处抛出异常
    } catch (e: Exception) {
        showError(e.message)
    }
}
```

#### 二、异常处理的注意事项
##### 1.结构化并发决定异常传播范围
协程通过**作用域（`CoroutineScope`）​**实现结构化并发，父协程的异常会传播到所有未完成的子协程（除非使用 `supervisorScope`）。

​**关键原则**​：避免在全局作用域（如 `GlobalScope`）启动协程，应使用与生命周期绑定的作用域（如 Android 的 `viewModelScope`、`lifecycleScope`），防止内存泄漏。
##### 2.区分“可取消异常”和“不可取消异常”
- ​**`CancellationException`**​：协程被取消时抛出的特殊异常（如调用 `job.cancel()`），通常不需要手动处理（协程取消是其生命周期的一部分）。
- ​**其他异常**​（如 `IOException`）：需根据业务逻辑处理，否则会导致协程取消并传播到父作用域。
##### 3.避免在 finally中执行不可取消操作
`finally`块中的代码默认**不会响应协程取消**​（因为 `finally`是 `JVM` 级别的终结逻辑），但如果其中包含**阻塞操作**​（如 `Thread.sleep()`）或**不可取消的挂起函数**，可能导致协程无法及时终止：
```kotlin
viewModelScope.launch {
    try {
        delay(1000)
    } finally {
        Thread.sleep(5000) // 阻塞 5 秒，协程无法在此期间响应取消！
    }
}.cancel() // 调用 cancel() 后，finally 中的 sleep 仍会执行完 5 秒
```
**解决方案**​：若需在 `finally`中执行必须完成的逻辑（如资源释放），可使用 `withContext(NonCancellable)`强制不可取消，但需确保其内部无长时间阻塞操作：
```kotlin
viewModelScope.launch {
    try {
        delay(1000)
    } finally {
        withContext(NonCancellable) {
            // 执行必须完成且不可取消的操作（如关闭文件）
            releaseResource()
        }
    }
}
```
#### 三、是否存在"取消不了的协程"？
协程的取消是**协作式**的（需主动配合检查取消状态），因此在某些极端情况下，协程可能无法被及时取消：
##### 1.执行不可中断的阻塞操作
若协程内部调用**非协程的阻塞 API**​（如 `Thread.sleep()`、`Socket.read()`、`java.util.concurrent`的阻塞方法），这些操作不会响应协程的取消信号，导致协程无法终止。
示例：
```kotlin
viewModelScope.launch {
    while (isActive) { // 检查取消状态
        Thread.sleep(1000) // 阻塞 1 秒，期间协程无法响应 cancel()
        doWork()
    }
}.cancel() // 调用 cancel() 后，Thread.sleep 仍会执行完当前周期
```
解决方案：使用协程提供的**可取消挂起函数**​（如 `delay()`替代 `Thread.sleep()`），这些函数内部会检查 `isActive`状态并在取消时抛出 `CancellationException`。

##### 2.在 `NonCancellable`上下文中运行
通过 `withContext(NonCancellable)`创建的上下文是**完全不可取消**的，协程在此上下文中的代码会一直执行到结束，即使父协程被取消。
**示例：**
```kotlin
viewModelScope.launch {
    withContext(NonCancellable) {
        delay(1000) // 可取消的挂起函数，但 NonCancellable 上下文会忽略取消信号
        Thread.sleep(5000) // 阻塞操作
    } // 必须执行完此处才会响应外部 cancel()
}.cancel() // 调用 cancel() 后，需等待 withContext 块结束才会真正取消
```
注意：`NonCancellable`应仅用于必须完成的清理操作（如释放资源），避免滥用。

##### 3.父协程已取消但子协程未感知
若父协程被取消，但子协程未通过 `isActive`检查或调用可取消函数，可能导致子协程继续运行。
**示例：**
```kotlin
val parentJob = viewModelScope.launch {
    launch { // 子协程 1
        while (true) { 
            // 无 isActive 检查，父协程取消后仍无限循环
        }
    }
    launch { // 子协程 2
        delay(1000) // 可取消，父协程取消后会抛出 CancellationException
    }
}
parentJob.cancel() // 子协程 1 继续运行，子协程 2 终止
```
解决方案：在协程循环中定期检查 `isActive`状态，或使用 `isActive`作为循环条件：
```kotlin
launch {
    while (isActive) { // 定期检查取消状态
        doWork()
    }
}
```
**总结：**
- ​**异常处理**​：优先使用 `try-catch`处理预期异常，`CoroutineExceptionHandler`处理全局未捕获异常，`supervisorScope`隔离子协程异常。
- **注意事项**​：遵循结构化并发（绑定生命周期作用域）、区分异常类型、避免 `finally`中执行不可取消操作。
- ​**无法取消的协程**​：主要出现在执行不可中断阻塞操作、`NonCancellable`上下文或未检查 `isActive`的无限循环中，需通过协程提供的可取消 API 避免。
