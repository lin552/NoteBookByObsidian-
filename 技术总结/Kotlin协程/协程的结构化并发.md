Kotlin 协程的**结构化并发（Structured Concurrency）​**是一种通过作用域（`CoroutineScope`）管理协程生命周期的设计模式，核心目标是解决传统并发编程中协程难以追踪、资源易泄漏、逻辑分散等问题。它通过明确的父子关系和作用域约束，让协程的执行更可控、更安全。

#### 一、结构化并发的核心思想

传统并发（如直接操作线程或使用 `GlobalScope`）的问题在于：协程的生命周期可能脱离业务逻辑的控制范围，导致“孤儿协程”无法被回收（例如 Activity 销毁后后台协程仍在运行）。而结构化并发的核心是：​**协程的生命周期必须被显式的“作用域”管理，且协程之间通过父子关系形成树状结构**，父作用域的状态（如取消、完成）会直接影响所有子协程。

#### 二、关键概念与机制
##### 1. `CoroutineScope`：协程的作用域边界
`CoroutineScope` 是一个接口，定义了协程的“生存范围”。每个协程必须属于一个作用域，作用域的生命周期决定了其中所有协程的生命周期。
- ​**作用域的创建**​：通常通过 `CoroutineScope(Dispatchers.Main + SupervisorJob())` 或绑定生命周期的对象（如 Android 的 `LifecycleScope`、`viewModelScope`）创建。
- ​**作用域的终止**​：当作用域被取消（调用 `cancel()`）时，其下所有未完成的协程会被递归取消（取消传播），确保资源释放。
##### 2. 父子协程的层级关系
每个协程启动时（如通过 `launch` 或 `async`），会隐式继承父作用域的上下文（`CoroutineContext`），并与父协程形成层级关系：
- ​**父协程取消 → 所有子协程自动取消**​：父作用域终止时，会触发所有子协程的取消（类似“级联取消”）。
- ​**子协程不影响父协程**​：子协程的完成或取消不会反向影响父协程（除非父协程显式等待子协程结果）。
例如，在 `CoroutineScope` 中启动一个子协程：
```kotlin
val parentScope = CoroutineScope(Dispatchers.IO)
parentScope.launch {
    // 子协程 1
    launch { /* 子协程 1.1 */ }
    launch { /* 子协程 1.2 */ }
} 
// 当 parentScope.cancel() 被调用时，子协程 1、1.1、1.2 都会被取消
```

##### 3. 取消传播（Cancellation Propagation）
结构化并发的核心机制之一是**取消的级联传播**。父作用域取消时，会递归遍历其所有子协程并触发它们的取消操作，避免“僵尸协程”残留。
- ​**取消的原因**​：可能是父作用域主动调用 `cancel()`，或父协程抛出异常（如 `Job` 被取消）。
- ​**协程的响应**​：每个协程内部通过检查 `isActive` 状态或捕获 `CancellationException` 来响应取消，释放资源（如关闭文件、网络连接）。

##### 4. 协程上下文（`CoroutineContext`）
`CoroutineContext` 是协程的“元数据集合”，包含：
- `Job`：管理协程的生命周期（取消、状态跟踪）。
- `CoroutineDispatcher`：指定协程运行的线程（如 `Dispatchers.Main`、`Dispatchers.IO`）。
- `CoroutineExceptionHandler`：全局异常处理器。
- 其他自定义键值对（如日志标签）。

在结构化并发中，子协程会继承父作用域的上下文（可通过 `CoroutineScope` 的 `coroutineContext` 属性访问），但也可以通过 `withContext` 显式修改部分上下文（如切换调度器）。

#### 三、结构化并发的优势
##### 1. 避免资源泄漏
通过将协程绑定到作用域（如 `viewModelScope` 绑定 `ViewModel` 的生命周期），当作用域终止（如 `ViewModel` 被销毁）时，所有未完成的协程会被自动取消，避免因后台任务未终止导致的内存泄漏或空指针异常。
##### 2. 逻辑清晰，易于调试
协程的父子层级关系让代码结构更直观（类似调用栈），调试时可以通过作用域快速定位协程的归属。例如，在 Android 中，`viewModelScope` 中的协程显然与 `ViewModel` 的逻辑相关，而 `lifecycleScope` 中的协程与 `UI` 生命周期绑定。
##### 3. 安全的异常处理
父作用域可以通过 `CoroutineExceptionHandler` 统一捕获子协程的异常，避免未处理的异常导致整个应用崩溃。子协程的异常也会触发父作用域的取消（除非使用 `SupervisorJob` 隔离子协程错误）。
##### 4. 更好的协作取消
结构化并发天然支持“协作式取消”：协程内部可以通过 `yield()` 或检查 `isActive` 主动让出资源，配合父作用域的取消指令，实现高效的资源管理。

#### 四、典型应用场景

##### 1. 生命周期绑定（Android）
Android 中通过 `lifecycleScope`（绑定 Activity/Fragment 的生命周期）和 `viewModelScope`（绑定 `ViewModel` 的生命周期）实现结构化并发：
```kotlin
// 在 Fragment 中启动协程，随 Fragment 销毁自动取消
viewLifecycleOwner.lifecycleScope.launch {
    // 执行网络请求或数据库操作
}
```

##### 2.批量任务管理
需要同时执行多个子任务并等待全部完成时，可通过 `coroutineScope` 函数创建临时作用域，确保所有子任务完成后才继续：
```kotlin
suspend fun fetchData(): List<Data> = coroutineScope {
    val task1 = launch { fetchFromNetwork() }
    val task2 = launch { fetchFromDatabase() }
    task1.join() // 等待任务1完成
    task2.join() // 等待任务2完成
    listOf(task1.result, task2.result)
}
// 若任意子任务取消或失败，整个作用域会被取消
```

##### 3.异步流程控制
使用 `async` 启动多个异步任务并组合结果时，`async` 返回的 `Deferred` 对象受父作用域管理，父作用域取消时所有 `Deferred` 任务会被终止：
```kotlin
val result1 = async { fetchData1() }
val result2 = async { fetchData2() }
val combined = result1.await() + result2.await() // 父作用域取消时，两个 async 任务都会被取消
```

#### 五、与非结构并发的对比

传统的非结构化并发（如直接使用 `GlobalScope.launch`）的问题在于：
- 协程的生命周期不受控（`GlobalScope` 是全局单例，无法被取消）。
- 协程之间无明确层级关系，难以追踪和调试。
- 容易因忘记取消导致资源泄漏（如 Activity 销毁后仍在执行网络请求）。

而结构化并发通过 `CoroutineScope` 和父子关系，将协程的生命周期与业务逻辑（如页面生命周期、任务上下文）绑定，从根本上解决了这些问题。
